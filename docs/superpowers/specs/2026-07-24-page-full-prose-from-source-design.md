# 页面完整文字稿：源材料摘取与加工正式方案

日期：2026-07-24  
状态：**已决议（用户同意 2026-07-24）**  
适用范围：CyberPPT Stage 01 内容页（仓库默认强制）  
关联：`references/script-quality.md`、`cyberppt.source_truth.v1`、`cyberppt.outline.v1`、既有 `script-audit`

---

## 1. 定位与判断

### 1.1 为什么这一层比“脚本上屏”更重要

上屏文字回答的是**怎么排**；完整文字稿回答的是**这一页到底要表达什么、取舍什么、不能说什么**。

若从源材料直接跳到上屏 bullet，会发生三类系统性失败：

1. **未完成论证**：把源段落裁成要点，读者看不到判断如何成立；  
2. **状态被抹平**：拟建议 / 待摸底 / 待基线被写成已确定；  
3. **越权表达**：本页写进了邻页问题或尚未到论证阶段的范围、投资、实施承诺。

因此，完整文字稿不是脚本的附属字段，而是 Stage 01 的**内容表达权威层**：

```text
Source Truth（可审计证据）
    → Outline 页合同（单页业务问题与证据分配）
        → 完整文字稿（本页业务表达与取舍）   ← 真正的内容表达
            → 上屏文字（同一表达的概括化、图形化派生；禁止并列、禁止双源头）
                → Stage 02 生产（视觉与模板）
```

**审稿优先级**：先审完整文字稿是否把业务说清楚且取舍正确；再审上屏是否忠实压缩；最后才进入生图。

### 1.2 完整文字稿是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 对本页业务问题的论证性短文 | 源文件相关段落的拼接 |
| 在 Outline 约束下的取舍结果 | Outline `main_message` 的同义扩写 |
| 可念、可审、可追溯的表达底稿 | 上屏模块标题的加长版 |
| 保留状态与边界的正式表述 | 为了好排版而提前写成的口号 |

---

## 2. 目标与非目标

### 2.1 目标

1. 规定内容页完整文字稿的**权威输入、摘取包、加工步骤、取舍规则与产出形态**。  
2. 使每一页文字稿都能回答：本页立什么判断、凭什么、继承什么、不写什么、交给下一页什么。  
3. 把“先业务后上屏”固化为仓库默认流程，而不是项目临时约定。  
4. 给出可机器检查的最小合同，以及必须留给人工审稿的判断项。  
5. 与现有 Source Truth / Outline / `script-audit` / Stage 02 兼容，不另起项目生命周期。

### 2.2 非目标（本期方案明确不做）

- 不自动从 DOCX 生成最终文字稿（生成代理仍负责改写；合同约束改写方式）。  
- 不把完整文字稿送入 ImageGen 作为最终上屏文字。  
- 不恢复旧 `ppt-script` 多角色总编运行器。  
- 不要求文字稿与源段落逐字相同。  
- 不在封面 / 目录 / 章节过渡页 / 封底强制文字稿。

## 3. 权威链与页内工件

### 3.1 权威顺序（冲突时以更高者为准）

1. **源材料原文**（经由 Source Truth 的 quote / locator 锚定）  
2. **Source Truth 记录**（type / status / conditions / claim_role）  
3. **Outline 页合同**（business_question / argument_role / source_refs / prerequisite_pages / main_claim_status / visual_center）  
4. **完整文字稿**（本页业务表达）  
5. **上屏文字**（压缩层）  
6. **讲解提示**（口头补充，不得引入新事实）

任何下层不得新增上层没有的事实、数字或状态升级。

### 3.2 单页最小输入包（摘取对象）

写本页完整文字稿前，必须先组装**页证据包**，不得直接打开源文件自由摘抄。

页证据包 = 

| 字段 | 来源 | 用途 |
|---|---|---|
| `page_id` / `title` | Outline | 页身份 |
| `business_question` | Outline | 本页只回答这一个问题 |
| `argument_role` | Outline | 决定能写什么、不能写什么 |
| `main_message`（大纲版） | Outline | 待文字稿校验或 refined 的判断句 |
| `source_refs[]` | Outline | 唯一允许使用的证据集合 |
| 每条证据的 `type/status/statement/quote/conditions/claim_role` | Source Truth | 摘取与改写原料 |
| `prerequisite_pages[]` 的主判断 | Outline + 已通过文字稿 | 承接句原料 |
| `visual_center` | Outline | 约束后续上屏同构，不反向决定文字稿论点 |
| `main_claim_status` | Outline | confirmed / proposed / conditional / unresolved |

### 3.3 单页产出

内容页脚本中强制包含：

```text
- 页面标题：
- 主判断：          # 由完整文字稿收敛出的一句话；可与 Outline 微调但不得改角色
- 完整文字稿：      # 本方案核心产出
- 上屏文字：        # 仅允许从文字稿压缩
- 证据：
- 边界：
- 视觉结构：
```

建议同时保留（可机器可选）：

```text
- 文字稿取舍说明：  # 本页故意不写什么、为何不写（1–3 句）
- 证据映射：        # 文字稿支撑点 → Source ID（若未内嵌也可单独列）
```

## 4. 摘取规则（从源材料到页证据包）

### 4.1 只摘 Outline 分配的证据

- **允许**：`source_refs` 中的全部 Source ID。  
- **禁止**：为了“写得更满”临时引入未分配 Source ID。  
- **例外**：前置页主判断的一句承接，不计入新证据，且不得展开其论证主体。

若写稿时发现本页问题无法仅用已分配证据说清：

1. 停笔；  
2. 回退 Outline / Source Truth（补证据或改页合同）；  
3. 不得在文字稿中“先写上再补 ID”。

### 4.2 摘取粒度

对每条 Source ID，摘取并保留四元组：

```text
命题 statement
原文 quote（或表格行原文）
状态 status
条件 conditions
```

数字必须保留：原值、单位、期间、口径（来自 `numeric` 或 statement）。

### 4.3 摘取时的类型纪律

| type | 文字稿中的合法用法 |
|---|---|
| F | 作为已发生 / 现状事实支撑 |
| J | 作为问题识别、变化解释、阶段判断 |
| R | 作为建设建议写入正文；方案体裁已含建议态，不必逐页标注“拟建议” |
| B | 作为边界、排除、暂缓、条件 |
| U | 作为待核 / 待摸底，不得改写成确定项 |

一条证据在文字稿中只服务一个支撑点；不得把 F 和 R 混成“已经具备建设方案”。

## 5. 加工规则（从页证据包到完整文字稿）

### 5.1 核心原则：论证性改写，不是摘要

加工 = 在 `business_question` 约束下，对证据包做：

1. **选择**：哪些证据进入本页主论证，哪些只作边界；  
2. **排序**：按论证需要重排，不按源章节顺序复述；  
3. **收敛**：形成本页唯一主判断；  
4. **降权 / 排除**：明确本页不写的相邻内容；  
5. **保真**：状态、数字、边界不升级、不发明。

### 5.2 固定四拍骨架（可合并段落，不可缺逻辑）

完整文字稿必须覆盖以下四拍：

1. **承接（Inherited）**  
   用一句话交代读者此刻已知什么（来自 `prerequisite_pages`）。若无前置，写情境起点，不编造前文结论。

2. **立论（Claim）**  
   明确本页要立住的判断，与最终 `主判断` 同义。只立一个。

3. **展开（Warrant + Evidence）**  
   对本页主题在源材料中的**主体内容**做完整论证展开，而不是只列 2–3 个上屏级要点。展开应达到「一小篇文章 / 一小章节」的完整性：读者不看源文件，仅凭本段也能理解该主题在材料中的主要事实、判断、条件与例外。每个关键支撑应能回溯 Source ID；数字保留原口径。

4. **边界与递交（Boundary + Handoff）**  
   - 本页**不**结论什么（对应 Outline 角色禁区 + 证据 status）；  
   - 下一页应接着回答什么问题（不得提前展开）。

### 5.2.1 完整性与颗粒度（已决议）

完整文字稿的篇幅与粒度**不对齐上屏文字**，而对齐：

> 源材料中，与本页 `business_question` / 主题相对应的那一部分**主体内容**。

具体要求：

1. **完整性**：应接近该主题在源材料中的主体论述覆盖面——关键事实、判断、条件、边界、必要展开都应进文字稿；不能为了“像 PPT 稿”而抽成疏纲。  
2. **文体**：写成可审阅的小文章或小章节（连续段落为主），不是模块标题 + 短句的预排版。  
3. **禁止上屏颗粒度**：若文字稿删去格式后仍与上屏 bullet 同级（短、碎、口号化），视为失败——它已失去作为业务表达层的意义。  
4. **仍受页合同约束**：完整性不等于把源文件整节无取舍粘贴，也不等于把邻页主题写进来；在本页问题边界内尽量写全，在角色禁区外坚决不写。  
5. **机器辅助**：不设绝对字数带（如 180–450）。机器侧继续拦截「相对主判断过薄」「与上屏近同」；是否覆盖源主题主体，以人工审稿 + 证据映射覆盖为主。

判断口令：

> 把本页完整文字稿交给未读源文件的业务同事，对方能否基本掌握该页主题在材料中的主体意思？  
> 若不能，文字稿过薄。  
> 若能，但读起来只是上屏要点的散文版，颗粒度错误。

### 5.2.2 文风：章节正文，禁止分析旁白（已决议）

完整文字稿必须是**源材料主题的正文改写**，读起来应像材料中的一小章节，而不是分析员对论证结构的旁白。

禁止写入正文的分析旁白（应改放到 `文字稿取舍说明` / `边界` / `讲解提示`）：

- 交代“本页要先确认什么、不要讨论什么”的调度句（如“首先需要确认…而不是直接讨论…”）；
- “从现有材料看 / 进入本页后 / 在确认…之后 / 本页只确认 / 本页不评价 / 本页回答的是”等元叙述；
- 用论证角色解释写作意图，而不是直接陈述事实、判断与边界本身。

正确做法：开篇即进入本页主题的实质内容（事实、变化、断点、拟建议等），按源材料逻辑展开；取舍与禁区用旁路字段显式记录。

### 5.3 按 `argument_role` 的取舍表（强制）

| argument_role | 必须写出 | 严禁写出 |
|---|---|---|
| foundation | 已存在的工作/数据/组织事实 | 首期范围、投资、建设路线、完整方案可行性 |
| change | 对象/尺度/服务需求如何变 | 解决方案模块清单、平台选型 |
| gap | 现有方式与新要求的断点 | “因此首期建设 X”的范围锁定 |
| necessity | 为何需要统一前期研究 | 正式立项结论、预算批复口径 |
| positioning | 拟定位、服务对象与职责分工 | 已建成、已审定范围、替代专业系统 |
| solution | 拟建能力/体系如何组织 | 把拟建议写成已上线能力 |
| scope | 首期聚焦、后续安排及筛选依据 | 把后续场景写成首期承诺 |
| implementation | 组织、近端任务、阶段节奏 | 无摸底依据的最终采购与部署细节 |
| assurance | 投入原则、验收与运行评价 | 把参考档位写成批复预算；把能力要求写成已定量化 KPI |
| decision | 下一步行动、关键证据准备与进入决策的路径 | 代替评审给出“同意立项”；拆成多页“已能/尚不能”边界巡检 |

### 5.3a 规划类汇报：边界从规划阶段就降权（强制）

前期研究 / 规划方案类材料，**页面规划**即不得把“强调边界”当作页使命：

1. 章节使命、页标题、`business_question`、`main_message` 写正向问题（建什么、怎么建、近期做什么），不写“尚非事实 / 可以 vs 不能 / 待确认清单”式问题。  
2. 完整文字稿以方案论证收束；“不等于 / 不构成 / 不代替 / 讨论稿不…”等降权句不得作为段落或整页高潮，一律进 `边界` 与 `文字稿取舍说明`。  
3. 上屏只压缩文字稿中的主题结构；不得单独从 Source Truth 的 status 字段另造边界旁白上屏。  
4. 全篇边界集中陈述最多一处（通常在决策/下一步页），禁止第四章末与第五章连续多页重复说教。  
5. 保留状态不等于逐页朗读状态：防升级靠字段与审计，不靠观众每页听到“还不是事实”。  
6. **方案体免盖章**：除现状/事实页外，材料体裁已是建议方案；正文与上屏禁止逐页重复“拟建议 / 尚属建议 / 建议性安排”。直接写“形成 / 覆盖 / 建立 / 推进”；封面“讨论稿”与必要时的 `边界` 已够用。

### 5.4 取舍必须显式化

每页完整文字稿的加工，至少完成三类取舍：

1. **证据取舍**：`source_refs` 中哪些进入主展开，哪些只进 `边界` 字段；  
2. **议题取舍**：源材料同节还有哪些内容故意不写（因属于邻页或非本页问题）；  
3. **强度取舍**：哪些只能写到“方向 / 拟建议 / 待确认”，不能写到“确定 / 建成”——强度约束写入 `边界` / `文字稿取舍说明`，不写入正文高潮或上屏模块标题。

若脚本中设 `文字稿取舍说明`，应用 1–3 句记录上述取舍。

### 5.5 禁止的加工手法

- 按源文件小标题顺序“一、二、三”复述后称作文字稿；  
- 把多页 Outline 的 `main_message` 拼进一页；  
- 用方法论套话（原则、框架、理念）替换业务对象与证据；  
- 为了上屏好看，先写模块再倒推文字稿；  
- 用常识补齐源材料没有的数据、排名、外部结论。

## 6. 与主判断、上屏文字的关系

### 6.1 主判断

- 主判断是完整文字稿的**一句话收敛**，不是并行的另一套结论。  
- 允许相对 Outline `main_message` 做表达打磨，但不得改变 `argument_role` 允许的主张强度。  
- 若文字稿写完后发现主判断需要大改：先改文字稿与页合同，再改上屏。

### 6.2 上屏文字（概括化 / 图形化派生，禁止并列与双源头）

上屏文字是完整文字稿的**概括化、图形化表达**：

- **概括化**：把短文章收成可上屏的模块与短句，不另起论证；  
- **图形化**：按 `visual_center` 把已有论证收成路径、对照、分层、矩阵等结构，便于排版与生图。

它**不是**：

- 与完整文字稿并列的第二套内容层；  
- 可各自从 Source Truth / Outline 分头摘取的独立源头；  
- 先写好的模块清单，再倒推文字稿的“排版草稿”。

派生规则：

1. 每个一级模块都能在完整文字稿中找到对应表述；  
2. 模块划分服务 `visual_center` 同构，不新增论点；  
3. 数字与状态词不得与文字稿冲突；  
4. 不得出现文字稿未表达的建议或边界放松；  
5. 证据 ID 的权威落点在文字稿侧的 `证据映射`；上屏不单独开辟第二条证据链。

压缩检查口令：

> 删掉上屏后，仅凭完整文字稿，业务读者仍应能理解本页；  
> 删掉文字稿后，仅凭上屏，业务读者不应被认为已经完成论证审稿；  
> 若上屏某条在文字稿中找不到对应，说明上屏越权或文字稿未写全——先改文字稿，再重压上屏。

### 6.3 Stage 02

- 生产 truth：`主判断` + `上屏文字` + 模板文字层锁定。  
- 完整文字稿：保留在脚本中，作为返工溯源、讲解与业务验收底稿，**不**画入 full 图。

## 7. 质量门禁

### 7.1 人工审稿门（主门）

大纲批准后、生图批准前，内容页必须能通过业务审稿。审稿人主要看完整文字稿，问题清单：

1. 是否只回答一个 `business_question`？  
2. 主判断是否被展开段真正支撑？  
3. 状态与边界是否与 Source Truth 一致？  
4. 是否越权写了本角色禁止内容？  
5. 取舍是否清楚（故意不写什么）？  
6. 下一页递交是否只提出问题、不提前展开？

未通过：返工文字稿；禁止用“先改上屏”绕过。

### 7.2 机器审计门（辅门，增强 `script-audit`）

在现有缺失 / 错序 / 过薄 / 近同上屏检查之外，增加：

| 代码 | 检查 |
|---|---|
| `CONTENT_PROSE_MISSING` | 已有 |
| `CONTENT_PROSE_AFTER_ONSCREEN` | 已有 |
| `CONTENT_PROSE_TOO_THIN` | 已有 |
| `CONTENT_PROSE_EQUALS_ONSCREEN` | 已有 |
| `CONTENT_PROSE_ONSCREEN_GRANULARITY` | 已有 |
| `CONTENT_PROSE_ANALYTICAL_VOICE` | 文字稿使用“本页只确认/首先需要确认…”等分析旁白，而非章节正文口吻 |
| `CONTENT_SELECTION_NOTES_MISSING` | 已有 |
| `CONTENT_EVIDENCE_MAP_MISSING` | 已有 |
| `PROSE_SOURCE_COVERAGE_GAP` | 文字稿未覆盖 Outline 分配的 P0 Source ID（可用显式映射或 ID 出现检查） |
| `PROSE_STATUS_UPGRADED` | 文字稿对条件态证据使用完成态措辞（复用现有状态词表） |
| `PROSE_ROLE_SCOPE_VIOLATION` | foundation/change/gap/necessity 等角色出现禁用议题词 |
| `ONSCREEN_NOT_GROUNDED_IN_PROSE` | 上屏模块关键词无法在文字稿中找到对应支撑（启发式） |

机器门不能替代人工对“论证是否成立”的判断；它只拦截明显的缺失、越权和状态污染。

### 7.3 建议的批次工作顺序

```text
对一批页面：
1. 组装页证据包
2. 写完整文字稿（可先不写上屏）
3. 业务自检四拍 + 角色取舍表
4. 收敛主判断
5. 压缩上屏文字
6. 填写证据 / 边界 / 视觉结构
7. script-audit
8. 用户审文字稿（可与脚本同批，但审稿焦点在文字稿）
```

允许“文字稿先行批次”：某批文件只含标题、主判断、完整文字稿、证据、边界；上屏稍后补。但进入 Stage 02 前必须补齐上屏并通过全字段审计。

## 10. 决策点决议

| 决策点 | 决议 |
|---|---|
| 审稿节奏 | 同批脚本确认；审稿焦点先完整文字稿、后上屏。允许文字稿先行自检，进 Stage 02 前必须补齐上屏。 |
| `文字稿取舍说明` | **强制**（1–3 句）。 |
| Source ID 露出 | **强制证据映射表**；正文不强制处处 `(S0xx)`。 |
| 篇幅与颗粒度 | **不对齐上屏**。完整性应对齐源材料中本页主题的主体内容，文体接近小文章/小章节；禁止上屏颗粒度的散文版 bullet。不设绝对字数硬阈值；机器保留过薄/近同上屏检查，主体覆盖以人工审稿与证据映射为主。 |
| 上屏与文字稿关系 | 上屏是文字稿的**概括化、图形化派生**；禁止并列关系，禁止各自从 Source Truth 分头摘取。 |

第 4 点已按用户意见修订：完整文字稿若按上屏颗粒度来写，即失去作为内容表达层的意义。

---

## 11. 结论

完整文字稿的正式定义是：

> 在 Outline 单页业务问题与 Source Truth 证据包约束下，对源材料进行选择、排序、收敛与降权后形成的论证性短文；它是内容表达与取舍的权威层，上屏只是其概括化、图形化派生，不得与文字稿并列或各自另开源头。

当前仓库已有“必须存在完整文字稿”的薄门禁；**本方案补上真正重要的部分：如何摘取、如何加工、如何取舍、如何审稿、如何与上屏和审计衔接。**

待第 10 节决议已获用户同意。阶段 A（合同固化）与阶段 B 最小机器门（取舍说明、证据映射、上屏颗粒度启发式）已落入 `references/script-quality.md`、`SKILL.md` 与 `script-audit`。
