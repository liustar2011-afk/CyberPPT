# `script_quality_contract.py` 模块化拆分设计

日期：2026-08-15  
状态：已实施
范围：仅拆分 `cyberppt/script_quality_contract.py`，不同时处理其他大型模块

## 一、背景与目标

`cyberppt/script_quality_contract.py` 当前约 5,800 行，混合承担数据模型、脚本解析、文本规则、屏显审查、源材料覆盖、视觉表达审查、跨页关系审查和总审计编排等职责。模块体积过大，导致规则定位困难、修改影响面不清晰、测试隔离成本高，也增加了后续维护和扩展风险。

本次工作的目标是按职责拆分该模块，同时保持现有调用方无感：

1. 保持现有公开导入路径可用；
2. 保持审计规则、错误码、检查顺序和输出结果不变；
3. 降低单个模块复杂度，建立清晰的依赖方向；
4. 为后续逐个拆分其他大型模块形成可复用方法。

本次不是规则重写、接口升级或审计逻辑优化。任何行为调整应作为后续独立任务处理。

## 二、设计原则

### 2.1 行为等价优先

拆分前后，对相同输入必须产生相同的：

- 解析结果；
- 问题数量和顺序；
- 问题代码、严重级别、页码和说明；
- 修复建议；
- 命令退出状态和序列化结果。

### 2.2 稳定入口优先

保留 `cyberppt/script_quality_contract.py`，将其改为兼容门面。现有业务代码和外部调用方无需立即修改导入路径。

### 2.3 单向依赖

子模块依赖方向应从基础模型和解析能力，逐层指向具体规则和总编排；子模块不得反向导入兼容门面，避免循环依赖。

### 2.4 小步迁移

按职责逐组迁移，每次迁移均通过针对性测试和完整回归测试。不得一次性机械切割全部代码后再集中修复。

## 三、目标结构

新增内部包：

```text
cyberppt/
├── script_quality_contract.py       # 稳定兼容门面，仅导入和再导出
└── script_quality/
    ├── __init__.py
    ├── models.py                    # 数据结构和类型
    ├── parsing.py                   # Markdown、字段、旁车和讲稿解析
    ├── text_rules.py                # 文本、标题和政企写作规则
    ├── onscreen.py                  # 屏显结构、密度和并列关系规则
    ├── source_coverage.py           # 源材料、证据和内容单元覆盖
    ├── presentation.py              # 页面表达、视觉结构和模板审查
    ├── relationships.py             # 跨页关系、前置条件和范围连续性
    ├── final_form.py                # 最终稿路径和稿件形态审查
    └── audit.py                     # 总审计编排和重试指令
```

### 3.1 `models.py`

承载稳定的数据结构、枚举、类型别名及其轻量方法，包括但不限于：

- `ScriptPage`；
- `ScriptDocument`；
- `ScriptQualityIssue`；
- 规则执行过程中共享的结构化结果类型。

该模块不得依赖任何具体审计规则。

### 3.2 `parsing.py`

承载脚本输入的结构化解析，包括：

- Markdown 页面切分；
- 字段块及字段顺序解析；
- 来源引用、段落映射和证据字段解析；
- 讲稿备注解析；
- sidecar 数据解析；
- `parse_script_markdown` 和 `parse_script_path`；
- 与解析直接相关的规范化辅助函数。

### 3.3 `text_rules.py`

承载文字层面的规则，包括：

- 政府公文式、政企交流材料的默认写作约束；
- 禁止口语化、空泛判断和不当对比句式；
- 标题、模块标题、判断句和正文措辞规则；
- 纯文本层面的稿件问题识别。

本次只迁移现有规则，不改变规则内容或阈值。

### 3.4 `onscreen.py`

承载单页屏显内容规则，包括：

- 层级完整性；
- 信息密度；
- 并列结构；
- 未标注屏显项目；
- ImageGen 输入准备度中与屏显文本直接相关的检查。

### 3.5 `source_coverage.py`

承载源材料忠实度和覆盖检查，包括：

- Source Truth 引用和证据覆盖；
- 段落、内容单元与脚本页面的映射；
- 内容遗漏、重复和无依据扩写识别；
- 面向人工复核的覆盖摘要。

### 3.6 `presentation.py`

承载页面呈现与视觉表达检查，包括：

- 页面表达结构；
- 视觉结构契约衔接；
- 模板或版式相关检查；
- 视觉载体和页面使命之间的适配检查。

### 3.7 `relationships.py`

承载跨页及业务关系检查，包括：

- 页面关系摘要；
- 前置条件；
- 对象、关系和限定条件连续性；
- 页面范围和事实强度跨页一致性。

### 3.8 `final_form.py`

承载交付稿最终形态检查，包括：

- 最终脚本路径约束；
- 最终稿完整性；
- 稿件形态和交付格式规则。

### 3.9 `audit.py`

承载总编排，不重新实现具体规则：

- `audit_script_quality`；
- 固定规则执行顺序；
- 汇总、排序和返回；
- `script_retry_directive` 等与审计结果编排直接相关的能力。

## 四、兼容性设计

### 4.1 公开接口

原文件保留为兼容门面，并显式再导出现有公开符号。现有导入继续有效，例如：

```python
from cyberppt.script_quality_contract import (
    ScriptPage,
    ScriptDocument,
    ScriptQualityIssue,
    parse_script_markdown,
    parse_script_path,
    audit_script_quality,
)
```

门面文件目标控制在约 200 行以内，只包含必要的导入、再导出和兼容说明，不承载规则实现。

### 4.2 私有辅助函数的过渡兼容

现有测试和少量内部代码直接导入以下划线开头的辅助函数。为避免本次重构引发无关调用方修改，这些符号在第一阶段仍由门面再导出。

该兼容只作为迁移过渡：

- 本次不删除；
- 在代码中标明其非稳定公共 API；
- 后续可通过独立任务将调用方迁移至正式接口，再决定是否移除。

### 4.3 `__all__`

门面和内部包均采用显式 `__all__`，避免通配导入意外暴露内部实现。兼容测试应固定当前需要保留的符号集合。

## 五、依赖约束

允许的主要依赖方向为：

```text
models
  ↑
parsing
  ↑
具体规则模块（text_rules / onscreen / source_coverage /
presentation / relationships / final_form）
  ↑
audit
  ↑
script_quality_contract 兼容门面
```

具体规则模块之间如需复用通用纯函数，应将纯函数下沉到语义最接近的基础模块或新增小型内部工具模块，不得通过互相导入形成环。

禁止：

- 子模块导入 `script_quality_contract.py`；
- 新增模块导入阶段的文件读取或环境探测（下述行为冻结例外除外）；
- 为解决循环依赖使用延迟导入作为常态方案；
- 将无关规则重新集中到新的“大杂烩”工具模块。

行为冻结例外：`onscreen.py` 继续在导入阶段通过
`MODULE_CEILING = _load_module_ceiling()` 读取既有 `rules.yaml`。该读取时点和
回退逻辑来自拆分前实现；本次为保证行为等价而原样保留，不代表允许其他模块新增
导入 I/O，也不再宣称内部包绝对没有导入期文件读取。后续应以独立任务冻结配置读取
时点、缓存与失败回退语义，再设计惰性加载或显式配置注入，并用行为快照验证迁移。

## 六、迁移策略

按以下顺序实施：

1. 建立兼容性和行为基线测试；
2. 提取模型；
3. 提取解析能力；
4. 按规则域依次提取文本、屏显、源覆盖、页面呈现、跨页关系和最终稿规则；
5. 提取总审计编排；
6. 将原文件收敛为兼容门面；
7. 运行模块依赖检查、针对性测试和完整测试。

每一步只进行代码搬迁、导入调整和最小必要的依赖解耦，不顺带修改规则、命名、文案或阈值。

## 七、测试与验收

### 7.1 兼容性测试

- 现有公开符号可从原路径导入；
- 当前仍被调用的私有辅助函数可从原路径导入；
- 现有命令模块无需修改或仅需内部非行为性导入整理；
- 不出现循环导入。

### 7.2 行为等价测试

选择覆盖主要规则域的固定输入样本，对拆分前后结果做结构化快照比较，至少包含：

- 问题总数；
- 返回顺序；
- `code`；
- `severity`；
- `page_id`；
- `message`；
- `fix_suggestion`；
- 解析后的页面和字段结构。

比较应基于结构化对象，不依赖不稳定的对象地址或运行时表示。

### 7.3 架构约束测试

- 兼容门面不再包含规则实现；
- 兼容门面不超过约定规模上限；
- 内部子模块不得反向导入兼容门面；
- 模块导入测试覆盖所有新增文件。

### 7.4 回归测试

- 先运行与脚本质量、语义意图、最终稿组装、ImageGen 交接相关的针对性测试；
- 再运行仓库完整测试集；
- 以当前完整测试基线为最低要求，不接受新增失败。

## 八、完成标准

满足以下条件方可认定本阶段完成：

1. `script_quality_contract.py` 已成为不超过约 200 行的兼容门面；
2. 主要职责已迁移至目标子模块，模块边界与本设计一致；
3. 现有导入路径和必要的过渡私有接口保持可用；
4. 拆分前后审计结果结构化对比一致；
5. 无循环依赖；
6. 针对性测试和完整测试全部通过；
7. 未夹带任何审计规则、事实强度、标题风格或输出文案变更。

## 九、不在本次范围内

- 拆分 `imagegen_handoff.py`、`validate_pptx.py` 等其他大型模块；
- 修改脚本质量规则、错误码、阈值或提示文案；
- 删除私有辅助函数兼容导出；
- 重构命令行接口；
- 调整 PPT 内容生成逻辑或政府公文式写作规则；
- 清理 Git 历史、运行产物或大型资产。

上述事项应在本阶段完成并稳定后，分别制定后续方案。

## 十、主要风险与控制措施

### 风险一：检查顺序发生变化

控制：在 `audit.py` 中保留原调用顺序，并通过完整问题列表快照验证，而非只比较问题集合。

### 风险二：隐式共享状态或常量遗漏

控制：迁移前梳理模块级常量和缓存；共享常量只保留单一权威定义，不复制多份。

### 风险三：私有函数实际已成为事实接口

控制：扫描仓库导入关系，为现有调用保留门面导出，并以测试固定过渡兼容范围。

### 风险四：循环依赖

控制：模型和解析层保持低依赖；规则模块不导入门面；增加全模块导入和依赖方向测试。

### 风险五：重构夹带行为优化

控制：本阶段采用严格行为冻结。发现可改进问题时只记录为后续事项，不在本次提交中处理。
