# CyberPPT-Stage02

CyberPPT-Stage02 is the visual-production half of the CyberPPT toolchain. It consumes an approved PPT semantic script and produces visual structure, generated page imagery, editable SVG/PPTX reconstruction and delivery QA.

## Product boundary

```text
CyberPPT-Script
Word / PDF → semantic PPT script
        │
        │ CyberPPT Final Script Contract
        ▼
CyberPPT-Stage02
script → visual structure → style lock → ImageGen → clean base → SVG → editable PPTX → QA
```

Source analysis, Outline planning and script authoring belong to `CyberPPT-Script`. This repository does not expose those Stage 01 workflows.

## Input

v0.1 accepts canonical `final-script.md` generated by CyberPPT-Script and legacy CyberPPT final scripts during migration.

Stage 02 reads the approved script without modifying it. Explicit business relations in `视觉结构` are projected into internal semantic relations; ambiguous pages remain reviewable instead of receiving invented relationships.

See `contracts/FINAL_SCRIPT_CONTRACT.md` and `docs/STAGE02_BOUNDARY.md`.

## Public CLI

Install from a checkout:

```bash
python -m pip install -e ".[test]"
```

Primary command:

```bash
cyberppt-stage02 --help
```

The `cyberppt` console command is retained as a migration alias and exposes the same Stage 02-only command boundary in this repository.

Main workflow commands:

```text
prepare-stage02-handoff
stage02-handoff-check
prepare-visual-structure
execute-visual-structure
record-visual-structure-execution
visual-structure-audit
final-script-pages
review-quick-page
```

High-fidelity editable production remains:

```bash
cyberppt-stage02 final-script-pages <project> \
  --script <final-script.md> \
  --pages <range> \
  --style-lock <visual_style_lock.json> \
  --production-build \
  --assembly-mode editable
```

## Semantic-to-visual boundary

Stage 02 uses three layers:

1. business semantic relation;
2. layout-neutral reading contract;
3. visual topology/composition selected by the visual-structure designer.

A business relation is never a one-to-one alias for a visual topology. For example, `evidence_supports` may become a convergence structure, while `layer_supports` may become a layered dependency structure.

## Style system

The default style library, Style 9 live contract, palette samples and visual-structure designer skill are part of this repository. Project style selection is persisted as `workbench/locks/visual_style_lock.json`.

## Editable production

The production chain keeps the existing high-fidelity route:

```text
audited full image
→ text-free clean base
→ authored SVG
→ vendored Quick assembly
→ Office render
→ text / geometry / visual QA
→ final PPTX
```

See the repository `SKILL.md` for the production contract.

## v0.1 extraction note

The first standalone release deliberately retains the internal Python namespace `cyberppt` and a compatibility subset of historical implementation modules. This preserves the mature ImageGen / Quick / QA chain while the repository boundary is separated. Those internals are not Stage 01 public APIs and can be pruned incrementally after dependency tests prove they are unused.
