# CyberPPT 专业单页脚本

只处理一张内容页。目标不是让字段齐全或审计通过，而是让这一页成为不可被相邻页替代的叙事、论证和信息表达单元；来源忠实与正式审计是底线，不是质量上限。

## 工作边界

- 先读适用 `AGENTS.md`，并按仓库要求先用 Graft 获取正式上下文。
- 只消费用户指定项目的当前事实源、语义理解、Source Truth、Outline、目标页和相邻页契约，不参考旧项目产物。
- 默认采用政府公文式、央企正式交流语体。不得改写已验证 Outline 的页面标题；如确需改名、重排或改变叙事路径，必须先修改权威 Outline 并重新验证，单页脚本不能自行覆盖标题。
- 用户要求分析或审阅时保持只读；要求编写或重做时只修改目标页及根因修复必需的正式上游契约。
- 轻量 Stage 01 只使用正式 `python -m cyberppt ... --lightweight` 命令；不创建 approval、receipt、attempt、escalation、ledger、哈希绑定或平行流程。
- 不合并最终全稿，不进入 Stage 02，不生成图片或 PPTX。

## 必读方法

每次任务先读 [references/professional-page-authoring.md](references/professional-page-authoring.md)。根据页面关系再读 [references/argument-and-visual-grammars.md](references/argument-and-visual-grammars.md)。需要写入正式 Markdown、评分或交付时读 [references/page-script-contract.md](references/page-script-contract.md)。

## 必读项目输入

按目标页所需范围读取：

1. Outline 中的页面使命、受众问题、核心信息、来源引用、内容单元、内容关系、禁止内容、后置内容和视觉意图。写上屏文字前必须逐条核对 `content_units[].onscreen_anchors`/`coverage_anchors`：这些是审计器要求逐字或高重合度出现在上屏文字/完整文字稿里的源文原句片段，不是写完再等审计报错才处理的选项。可以先运行 `python -m cyberppt preview-page-anchors '<project>' --page <page_id>` 直接列出目标页每个内容单元的锚点原文、长度（并标出是否已超过 `ONSCREEN_DETAIL_PHRASE_TOO_LONG` 的 30 字上限）和来源引用，不必手动翻 `outline.json`。同时读取页面的 `argument_role` 和（如存在）`expression_model_selection`：前者决定该页是否允许在上屏顶层模块标题中出现"缺口/不足/风险"等负面前景词（只有 boundary/security/quality/compliance/risk/assurance/foundation 等角色允许），后者的 `source_mapping` 中若某槽位标记为 `complication`/`problem`/`gap` 且非 `implicit`，同样可以豁免负面前景检查。
2. Source Truth 中全部相关事实、主体、动作、对象、条件、状态、数字、来源单元和语义节点。
3. `source-units.jsonl` 中对应正文、列表或表格原文，核对来源顺序与标题路径。
4. 前后页的页面使命、核心结论、页面落点和保留内容。
5. 目标页现有完整稿、上屏文字、视觉结构、备注和审计结果。

## 专业创作流程

### 1. 先建立页面设计简报

写作前明确：

- `storyline_role`：本页在整套叙事中承担什么角色。
- `receives_from_previous`：从上一页接收的事实、问题或判断。
- `audience_question`：本页独立回答的一个关键问题。
- `page_proposition`：来源支持、可判断、包含主体与关系的单句命题。
- `hands_to_next`：交给下一页的结论或待解问题。
- `non_substitutable_value`：本页相对前后页新增且不可替代的价值。
- `decision_boundary`：本页不能越过的状态、条件和内容边界。

如果这些字段无法同时成立，先报告页面使命或页间划分问题，不用文案掩盖结构缺陷。

### 2. 选择一条主论证链

从来源关系而不是版式偏好出发，选择一个主论证原型。允许辅助关系，但只能有一条支配阅读顺序的主链。常用原型及其适用条件见 `argument-and-visual-grammars.md`。

主链必须说清：

- 要证明什么；
- 哪些事实直接证明；
- 事实之间是什么关系；
- 受众读完应得到什么判断；
- 哪些边界阻止结论被过度推导。

### 3. 建立证据架构

将证据按论证职责分为：

- `claim`：直接支撑页面命题的核心事实；
- `reason`：解释原因、机制或关系的事实；
- `instance`：使抽象判断具体化的业务对象、场景、数字或案例；
- `boundary`：条件、状态、责任、权利或适用范围；
- `trace_only`：只用于追溯，不承担受众阅读任务的细节；
- `metadata`：题名、作者、日期、目录和章节标题，不得进入内容页论证。

每条进入页面的事实必须有明确职责。重要事项未经用户明确决定不得舍弃；压缩只能改变层级和呈现方式，不能改变事实归属、关系或状态。

对每条拟上屏事实做“直接推进测试”：删除该事实后，受众是否仍能从本页核心证据到达页面命题。行业属性、材料背景、广泛相关事实和一般前提若只提供远端语境，而不直接解释本页的变化、需求、缺口、机制或结论，应保留在完整稿或讲解层，不得因来源顺序靠前或标为 `premise` 就独立上屏。

### 4. 先写完整文字稿

完整稿是页面论证的母稿，不是原文拼接、审计关键词堆叠或演讲口语。根据论证需要组织为若干语义段，通常依次完成：提出命题、展开关键事实、解释关系、形成页面落点并保留边界。

必须保留来源中的业务对象、主体、动作、处理对象、条件、状态、数字和专有业务词。不得制造来源未支持的因果、确定性、优先级或价值判断。

正式脚本的完整文字稿、上屏文字和备注不得使用“不是……而是……”“而非”“非……而……”及其他以否定前项衬托正项的近义句式；直接以正向的“主体—动作—条件/结果”陈述判断。

页面标题以已验证 Outline 为准，包括源材料明确使用的边界、问题和不足类标题，不得为追求正向叙事自行改写。标题以下的正式脚本使用正式、稳健、克制的政府公文式表达，严格保留源材料的事实强度、条件、责任和状态。

### 5. 压缩为可独立阅读的上屏文字

上屏不是完整稿的摘要，也不是标签清单，而是论证结构的屏幕化表达：标题负责定题，核心结论负责定向，各信息模块分别承担事实、关系或落点。脱离讲解后仍应能回答本页问题。

模块应同维度、层级可辨、关系显式；流程要有顺序，矩阵要有双轴，分层要有上下位，闭环要有反馈对象和回流方向。不要用演讲者备注补救上屏核心信息缺失。

数字编号只承担真实顺序信号。只有来源和主论证链明确存在流程、阶段、时间、优先级、门控或其他顺序时，才使用 `1、2、3` 或 `①②③`；并列分类、职责、能力、对象、边界和条件使用无编号业务小标题，避免给受众造成流程暗示。

短语化前先识别同级条目的共享语义与差异语义。共享标题、谓词、对象、限定语或结果由父级分组或总括语承载一次，子项只保留各自新增的信息。不得把“共享明细 B”复制成“A1+B”“A2+B”两条；应组织为“共享父级 A—差异子项 A1、A2”，或在两个条目确有独立命题时分别写出不同的事实增量。

明细较短时可使用”标签：短语”。明细较长时，以”业务小标题 → 完整、自然的明细句”组织：业务小标题概括同一业务维度，其下每条明细保留完整命题；小标题与明细必须是真实的”概括—展开”关系。不得用”需求、措施、价值”等通用写作标签替代业务对象，也不得把”随着、通过、根据、围绕、面向”等状语或介词结构从主句中截断。一个小标题下有多条明细时，各明细必须回答同一个分类问题并承担相同论证职责；属性、变化、需求、缺口和应对不得伪装成并列明细。

**压缩枚举清单时，先数清楚完整文字稿里这条清单有几项，再决定怎么压。** 真实出现过的问题：完整文字稿里”平台受控处理、源端单方处理、多方留域联合计算（通过隐私保护计算、数据沙箱、可信执行环境完成）”是三种并列的数据处理方式，压缩上屏时随手写成”处理方式：平台受控处理或源端单方处理”，第三种——恰恰是最能体现”可信”技术特征的那种——整个消失了，不是被精简，是被遗漏了。具体检查方法：

- 数清楚这是几项的枚举（3～5 项的”小清单”最容易在压缩时整项漏掉，风险最高；6 项以上的长清单本来就要挑代表性的写，不在此列）。
- 决定压缩到几项时，问自己”被留下的和被去掉的，业务分量是不是明显不对等”——如果去掉的那一项是清单里技术含量最高、最能体现方案差异化价值的那个（比如”可信执行环境”之于”平台受控处理”），大概率不该丢，要么留下、要么换一种更短的说法保留关键词，不能整项消失。
- 确实要精简到少于全部项数时，上屏那句要么把留下的项写全，要么用”等”字收尾（如”平台受控、源端单方等多种方式”），明确告诉读者这是有意精简、不是清单的全部——不写”等”字、又不是全部项，等于让读者以为这就是完整清单，这是真正的问题所在，不是”字数超没超”的问题。
- 这一步没有机械检查能完全兜底（`script_quality/source_coverage.py::_onscreen_enumeration_loss_issues` 试过用枚举项计数做审计层面的自动提示，两轮调参后仍然噪音过大而未接入默认审计——语义判断”这次压缩合不合理”本身就不是纯计数能分辨的），所以这一步必须在写的当下就做对，不能指望写完了让审计工具兜底。

### 6. 把语义关系翻译成视觉语法

视觉结构须定义入口、视觉中心、主轴、节点、连接关系、阅读顺序和出口。先识别构成、流程、因果、缺口、对比、条件、协同或反馈关系，再选择相应视觉语法；不得先选“三栏、卡片、环形图”再强塞内容。

### 7. 写演讲者备注

备注用于展开证据、解释条件和完成页间过渡，不复述制作过程，不包含审计说明，也不承担页面核心命题。

## 诊断与重写顺序

分析现有页面时，按以下优先级判断：

1. 页面使命是否成立，是否与相邻页重叠或断裂；
2. 页面命题是否清晰、可证且未越界；
3. 主论证链是否闭合，关系方向是否正确；
4. 证据是否真正承担论证职责；
5. 信息架构是否形成层级与阅读顺序；
6. 完整稿、上屏文字、视觉结构和备注是否各司其职；
7. 最后才检查格式、字数和审计规则。

不要把诊断退化为问题清单。必须先给出当前页面的真实逻辑、核心缺陷及其影响，再提出可执行的重构方案。

## 硬门槛与专业评分

来源漂移、关系写反、状态升级、重要事项遗漏、越过 `must_not_include` 或抢写 `reserved_for_later` 均为硬阻断，不能用评分抵消。

通过硬门槛后，按 `page-script-contract.md` 的 100 分量表评价专业质量。低于 90 分不得称为“可提交人工门”；审计通过也不能替代专业评分。

## 正式验证

人工审阅后，只对目标页所在正式稿运行轻量审计：

```powershell
python -m cyberppt script-audit '<project>' --input '<authoritative-page-or-chapter-script>'
```

当前 CLI 默认输出 `mode: lightweight`，不接受额外的 `--lightweight` 参数。

先判断问题属于页面写作、Outline 契约、Source Truth 角色或状态，还是检查器误报；修复根因，不添加重复锚点句、虚假结论、空模块或同义词替换来消除错误码。局部修改不触发无关上游或全稿级联重审。

## 交付

完整展示页面设计简报、主论证链、完整文字稿、取舍说明、上屏文字、证据映射、视觉结构、建议理由、专业评分、残余风险和审计结果，并提供全部真实产物的绝对可点击路径。随后停下等待用户确认。
