# PPT脚本质量与审计

## 执行时点

在 Outline 通过并获得用户批准后编写批次脚本。每个批次完成后对 `workbench/scripts/drafts/` 下的批次稿运行 `script-audit`。全稿定稿前先运行：

```bash
python -m cyberppt assemble-final-script <project>
```

再对 `workbench/scripts/final/script-final.md` 做全稿 `script-audit`。定稿文件不得出现「草稿」「批次」字样或批次横幅；`script-audit` 对 `scripts/final/` 路径会以 `FINAL_MANUSCRIPT_DRAFT_BANNER`（error）拦截。脚本审计未通过时不得批准脚本或进入 Stage 02。

审稿优先级：先审**完整文字稿**是否把本页业务说清且取舍正确；再审上屏是否忠实压缩；最后才进入 Stage 02。完整文字稿是内容表达权威层，不是上屏附属字段。详细设计见 `docs/superpowers/specs/2026-07-24-page-full-prose-from-source-design.md`。

## 页面合同

- 封面、目录、章节过渡页和封底使用模板页结构。
- 章节过渡页只写“第X章：XXX”。
- 内容页保留：页面标题、主判断、完整文字稿、文字稿取舍说明、证据映射、上屏文字、证据、边界、视觉结构、讲解提示，以及 **`【演讲者备注】`**（组装写入 PPT 备注）。
- 一页只回答一个完整业务问题，并由一个视觉中心承载。

## 完整文字稿（内容页强制 · 仓库默认）

内容页必须先完成业务表达与取舍，再压缩为上屏结构。不得从源材料或 Outline 直接跳到上屏 bullet。不依赖项目另行声明。

### 权威链

```text
Source Truth → Outline 页合同 → 完整文字稿 → 上屏文字 → Stage 02
```

下层不得新增上层没有的事实、数字，也不得升级证据状态。完整文字稿与上屏不是并列关系：上屏只派生自文字稿，不得与文字稿各自直接从 Source Truth / Outline 分头摘取。

### 字段顺序

```text
页面标题
→ 主判断
→ 完整文字稿
→ 文字稿取舍说明
→ 证据映射
→ 上屏文字
→ 证据 / 边界 / 视觉结构 / 讲解提示
→ 【演讲者备注】
```

## 演讲者备注（内容页强制 · 仓库默认）

内容页必须提供可上台照讲的演讲词，供 Stage 02 组装写入 PPT 备注。正式写法：

```markdown
【演讲者备注】

中电联已经具备开展相关研究的现实基础。……（正式汇报讲稿，约 1–2 分钟）
```

也兼容字段写法 `- 演讲者备注：`。组装入口 `page_notes_text` **优先消费**该区块；送图 ImageGen **不编入**演讲词。

封面、目录、章节过渡页和封底同样优先消费显式 `【演讲者备注】`。未提供时，组装器只生成与页面角色对应的简短正式话术，不得退回“本页围绕 / 核心提示 / 汇报要点”式正文转储。

### 正式汇报讲稿纪律（代码审计）

- 直接从本页核心判断或事实结论起笔，不称呼听众，不说明“现在准备讲什么”。
- 使用适合朗读的完整书面句，按“判断—依据—含义或边界”组织，避免主持式串场。
- **禁止**翻页元话语：`这一页` / `下一页` / `上一页` / `本页我们` / `本页先` / `本页把` / `本页只` / `看这一页` / `从这一页`。
- **禁止**主持式元话语：`各位同事` / `先把……说清楚` / `先说明` / `先谈` / `综合起来` / `接下来看` / `请先记住`。
- 页面承接依靠内容本身的因果、递进和边界，不单独编写转场口号。
- 强度与讨论稿一致，不升格成已立项、已建成。

### 审计级别

- `CONTENT_SPEAKER_NOTES_MISSING` / `CONTENT_SPEAKER_NOTES_TOO_THIN` / `SPEAKER_NOTES_SLIDE_META` / `SPEAKER_NOTES_HOST_META` → **error**
- 重试策略：`speaker_notes_naturalize`

### 摘取：页证据包

写文字稿前只组装 Outline 分配给本页的 Source ID；保留每条的 statement / quote / status / conditions / claim_role。禁止为写满而引入未分配证据。若证据不够写清本页问题，回退 Outline / Source Truth，不得先写后补。

### 加工：论证性改写

在 `business_question` 与 `argument_role` 约束下对证据包做选择、排序、收敛与降权。默认按“判断 → 依据 → 含义”组织；边界不是每页必写的第四拍。只有当页面主题本身就是范围、准入、投资假设或决策条件时，才把相关约束作为业务内容展开。

### 完整性与颗粒度（已决议）

完整文字稿的篇幅与粒度**不对齐上屏文字**，而对齐：

> 源材料中，与本页主题 / `business_question` 相对应的那一部分**主体内容**。

- 写成可审阅的**小文章或小章节**（连续段落为主），使未读源文件的业务读者仍能基本掌握该主题主体意思。
- **禁止上屏颗粒度**：不得写成模块标题 + 短句的散文版 bullet；否则失去作为内容表达层的意义。
- 完整性不等于整节粘贴，也不等于写入邻页主题；在本页问题内写全，在角色禁区外不写。
- 不设绝对字数硬阈值。

### 文风：章节正文，禁止分析旁白（已决议）

完整文字稿必须是**源材料主题的正文改写**，读起来应像材料中的一小章节，而不是分析员对论证结构的旁白。

禁止写入正文的分析旁白（应改放到 `文字稿取舍说明` / `边界` / `讲解提示`）：

- 交代“本页要先确认什么、不要讨论什么”的调度句（如“首先需要确认…而不是直接讨论…”）；
- “从现有材料看 / 进入本页后 / 本页只确认 / 本页不评价 / 本页回答的是”等元叙述；
- 用论证角色解释写作意图，而不是直接陈述事实、判断与边界本身。

正确做法：开篇即进入本页主题的实质内容（事实、变化、断点、拟建议等），按源材料逻辑展开；取舍与禁区用旁路字段显式记录。

### 强制旁路字段

- `文字稿取舍说明`（1–3 句）：本页故意不写什么、哪些证据只作边界、强度为何停在拟/待。
- `证据映射`：支撑点 → Source ID；Outline 分配的 Source ID 必须在映射中出现。正文不强制处处 `(S0xx)`。

`reserved_for_later`、`boundary_refs`、`boundary_constraints` 及由其形成的
`边界`内容只用于内部选材、强度和跨页审计。不得把这些内部控制自动复制到
`完整文字稿`、`上屏文字`、`讲解提示`或`【演讲者备注】`。尤其禁止在讲解层
写“反复区分”“避免听众误解”“不要讲成”“不是承诺”等防御性教练话术。
页面主题确实是范围或决策条件时，应直接陈述业务范围或条件，不得改写成
提醒汇报人防止误解的元话语。

### 上屏与 Stage 02

上屏文字是完整文字稿的**概括化、图形化表达**，不是与文字稿并列的第二套内容层，也不是另一条可独立溯源的写作源头。

内容页默认采用“短标题 + 判断型副标题 + 正文证据层”三级结构：

- `页面标题`只写主题，保持简短；
- `副标题`由`主判断`压缩而来，通常不超过30个汉字，优先保留关键数字、对象和结论，不承载解释性细节；
- `上屏结论`保留完整判断作为语义构图元数据；当副标题已经承载判断时，必须使用`semantic_only`，不得在正文区重复绘制；
- `上屏文字`只展开证据、关系、边界和业务含义，不重复页面标题或副标题，不再设置第二个通栏大标题。
- **模块标题标点层级**：上屏文字中的一级模块标题（如 `### 一、模块`）若包含“标题＋小结”两段，标题与小结之间使用 `｜`；结论先行的正文 bullet 才使用 `：`。禁止上级模块标题和下级小结标题同时用冒号造成层级混淆。

- **派生关系**：先有完整文字稿，再从上屏压缩；每个一级模块与要点必须能在文字稿中找到对应表述。
- **禁止并列**：不得“文字稿写论证、上屏另起炉灶写模块”；也不得先写上屏再倒推文字稿。
- **禁止双源头**：Source Truth / Outline 只进入完整文字稿（及证据映射）；上屏不得绕过文字稿直接从证据表或大纲另摘论点、数字或边界。
- **图形化**：模块划分服务 `visual_center` 同构（路径、对照、分层、矩阵等），把文字稿已有论证收成可上屏结构；不创作新论点。
- **禁止边界旁白上屏**：上屏 bullet 只写本页主题事实与结构；“不等于… / 不能只看… / 不写成… / 不等于已完备”等降权旁白放进 `边界` 或送图【禁止项】，不得塞进核心模块短句。
- **边界默认关闭**：边界不是“论证完整”的固定第四模块。只有页面主题本身是范围、准入、安全、治理、质量、合规、风险、保障、部署、容量、降级或验收时，边界/约束才允许成为上屏内容。资产、能力、场景、路径等普通主题页出现“质量边界 / 质量要求 / 安全边界 / 约束条件”等模块，审计必须报 `OFF_TOPIC_CONSTRAINT_MODULE` 并阻止生图。
- **主题取舍优先于完整性套话**：上屏内容的取舍标准是是否服务于本页 `business_question` / 主题，不是“是否显得完备”。若完整文字稿已经把本页主题讲清楚（事实、结构或论证已经自洽），上屏不得为了显得“更完整”而追加“仍需完善 / 有待完善 / 有待提升 / 尚待健全 / 持续优化”一类无事实、无边界内容的评价性收尾；这类套话不来自 Source Truth，也不构成本页判断或边界，只会冲淡主题焦点、伪造“论证还没写完”的错觉。是否收尾评价取决于本页主题本身是否就是差距、必要性或提升路径的论证对象，不是逐页配平的写作习惯——与既有基础事实无关的完善类收尾一律删除，判断标准同 `工作基础页只陈述事实基础`。
- **规划方案正向表述（规划→文字稿→上屏贯通）**：前期研究/规划类汇报以方案论证为主，不是现状审计或边界巡检。从章节使命、页标题、`main_message`、`business_question` 起就写“建设什么 / 如何组织 / 如何推进”，不要规划成“可以 vs 不能 / 尚非事实 / 待确认清单”页。完整文字稿同样用正向论证收束，禁止每段或每页以“不等于… / 不构成… / 不代替… / 讨论稿不…”作高潮；状态与禁区写入 `边界` 与 `文字稿取舍说明`。上屏从文字稿压缩时不得把这些旁白再塞回模块标题或 bullet。专属决策/缺口页可集中陈述推进条件，且全篇最多一处，禁止拆成多页重复。
- **方案体免逐页盖章**：除现状/事实页外，全篇默认即是建议方案。正文与上屏直接写建设内容（形成、覆盖、建立、推进），禁止逐页重复“拟建议 / 尚属建议 / 建议性安排 / 表述为拟建议”。防升级靠封面“讨论稿”、全篇体裁与必要时的 `边界` 字段，不靠每页盖章。
- Stage 02 生产 truth 仍是主判断 + 上屏文字 + 模板层；完整文字稿留在脚本中作业务审稿与返工溯源，不画入 full 图。

### 上屏明细短语化与构图元数据隔离（代码门禁）

`完整文字稿`可以保留源材料主题的小文章；`上屏文字`是读者直接阅读的结构层，明细不得把完整句群或源材料段落原样搬入。每条带“标签：内容”的明细优先写成一个短语或一个短句：冒号后的有效中文/英文/数字字符数不超过 **36** 为推荐区间，**37–60** 触发 `ONSCREEN_DETAIL_PHRASE_TOO_LONG` warning，超过 **60** 触发同一代码的 error 并阻断脚本批准。应拆成多条同维度短语、提升模块层级，或把完整判断放回独立字段后再压缩；不得在组装层静默截断。

主判断、法律边界和确有必要的完整结论可以保留长句，但必须分别归入 `主判断`、`上屏结论`、`边界` 或 `完整文字稿` 等字段，不要伪装成上屏明细。这样既保留事实与法律精度，也避免一个卡片、泳道或矩阵单元承载一整段解释。

构图元数据不得进入 `上屏文字（严格锁定）`。`四行选择矩阵`、`阅读顺序`、`视觉中心`、`构图说明`、`矩阵/泳道/色块/主链的呈现说明`、`非并列`、`控制链层面`、`权利对象层面` 以及 `第X行｜` 这类坐标或排版指令，也不得转存到 `视觉结构（不上屏）` 规避检查；Stage 01 只保留它们对应的业务关系、方向和文字归属，具体构图由 Stage 02 视觉结构设计器决定。进入上屏时以 `ONSCREEN_LAYOUT_META_LEAK`（error）阻断，进入视觉结构交接时以 `VISUAL_STRUCTURE_LAYOUT_RECIPE`（error）阻断。业务本身的可见标签（例如“四种合作方式”“五个环节”）不因包含数量词而被禁止。

这两类门禁发生在 Stage 01 脚本写作/审计阶段。Stage 02 只消费已经锁定的上屏文字；组装器不得通过删字、截断或改写来掩盖脚本颗粒度问题。

### 角色取舍（摘要）

foundation / change / gap / necessity 不得提前写入首期范围、投资、建设锁定结论；positioning / solution / scope / implementation / assurance 直接写建设内容与组织方式，强度禁区写入 `边界`（且不必每页重复“此为建议”）；decision 用正向下一步收束，不拆成多页“已能/尚不能”对照。详见设计方案 §5.3。

## 章内推进

- 按 Outline 的 `argument_role` 和 `prerequisite_pages` 推进。
- 工作基础页只陈述事实基础。
- 环境变化页说明新要求。
- 断点页说明现有方式与新要求之间的差距。
- 必要性页只推导研究必要性。
- 定位、建设范围、实施、保障和决策内容只在对应前置条件满足后出现。

## 来源、边界与状态升级

- 每个内容页使用 Outline 分配的 Source ID。
- 方案汇报中，正文/上屏默认用直接语气陈述建议内容；“拟建议、尚属建议、建议性…”不得作为逐页戳记。确需防升级时，用封面体裁说明或单页 `边界`，不在模块标题和 bullet 前缀堆“拟”。
- “待确认 / 待摸底 / 待基线 / 暂缓 / 后续验证”仅在该页业务确实讨论分期或准入条件时使用，且写成分期安排，不写成“这还不是事实”的旁白。
- 不得把建议内容写成已经建成、正式确定或无条件承诺——靠体裁与字段约束，不靠逐页说教。

## 跨页重复

- 完整业务问题只在一页展开。
- 邻页可以短句回指，不复制前页主判断和论证主体。
- 本页与前页相似时，优先判断是否需要合并、改为承接句或推进到新的业务问题。

## 上屏结构与语义图同构

上屏是完整文字稿的图形化派生，但 Stage 01 只锁定内容关系，不提前锁定页面版式。`视觉结构（不上屏）` 是交给正式 Stage 02 `ppt-visual-structure-designer` 的语义合同；Stage 02 依据该合同比较构图候选、选择空间语法和媒介，不得把 Stage 01 的临时排版设想当作固定蓝图。

### 内容驱动的语义结构

- 先有主判断与完整文字稿，再划分上屏模块；不得从「有 N 项内容」反推 N 张同权卡片。
- 每页只保留一个核心判断和一种主业务关系；次级关系必须明确从属，不得再建第二套流程、结果链或总结链。
- 业务角色、对象、动作、状态、边界和结果必须与上屏文字建立归属关系；不得用一个抽象中心框把互不相关的文字强行汇聚。
- Stage 01 不指定媒介、载体、行列、方位或容器数量；这些属于 Stage 02 的候选比较结果。

### `视觉结构（不上屏）`语义合同

使用一段简短文字同时说明：

1. **主关系**：支撑、流转、转化、汇聚、分支、依赖、对比、控制、边界、责任或反馈中的一种主要业务关系；
2. **语义焦点**：核心判断落在哪个业务对象、动作、状态或结果；
3. **角色与方向**：参与关系的主体或对象，以及业务意义上的先后、输入输出、内外或上下级关系；
4. **文字归属**：各组锁定文字分别解释哪个对象、动作、边界或结果；
5. **表达自由**：不预设具体载体、媒介和页面几何，除非源材料本身明确要求某种图表。

合格示例：

> 五类服务共享同一服务定义并面向客户使用形成分支；五类名称分别归属对应服务对象，规格说明从属于统一服务关系；不预设具体载体、行列或位置。

不合格示例：

> - 主视觉以五条横向泳道排列，右侧设置统一收束条。
> - 中央放置服务引擎，四周用放射线连接各模块。
> - 左侧放完整文字，右侧放行业配图。
> - 简洁现代的科技风信息图。

### 同构信号

- 流程、阶段或反馈关系必须在主判断、完整文字稿或上屏文字中具有事实依据；视觉结构不得新增步骤和回流。
- 分层、支撑、控制或边界关系必须能回指已批准的主体、对象、状态或约束。
- 声明N类、N项或N步时，上屏内容保持事实数量完整，但该数量不得自动变成N个等权视觉容器。
- 逻辑骨架与视觉结构只能表达同一条主关系；若两者出现不同的起点、终点、结果或中心，退回 Stage 01 修正。

### 默认反模式

除非业务关系真正需要，默认避免：等宽卡片墙、六宫格、Bento 泛用、中心圆加周边图标、网页后台/数据大屏腔、紫蓝霓虹装饰话术。

### 审计级别（构图类）

- `VISUAL_STRUCTURE_LAYOUT_RECIPE`：视觉结构包含固定行列、泳道、卡片、中心载体或方位配方 → **error**
- `VISUAL_STRUCTURE_MULTIPLE_PRIMARY_NARRATIVES`：视觉结构另设第二套流程、结果链或总结链 → **error**
- `VISUAL_STRUCTURE_STYLE_ONLY`：仅风格词、无业务关系 → **error**
- `VISUAL_STRUCTURE_TOO_THIN` / `ONSCREEN_ANTI_PATTERN` → 初版 **warning**（不阻断通过；仍写入报告）
- 构图类失败的重试策略归属 `semantic_diagram_realign`

## 页面密度

- 内容页默认使用2—5个一级业务模块。
- 超过5个模块时使用明确分组、阶段或层级。
- 只有标题和口号的页面应补足证据或与相邻业务问题合并。
- 筛选条件、评价方法和工作方法只用于解释实际业务取舍，不独立抢占主体页面。

## 定稿形态

- `workbench/scripts/drafts/`：允许批次标题、`> 批次：`、草稿状态等过程标记。
- `workbench/scripts/final/`：只接受连续全稿；不得含「草稿」「批次」字样，也不得含「待 script-audit 通过后审稿」类过程提示。
- 合稿入口：`python -m cyberppt assemble-final-script <project>`；合稿失败或仍含过程标记时不得进入全稿批准。

## 失败重试

读取 `retry_scope` 和 `retry_directive`，只重写失败页面并保留有效来源、状态和页面合同。文字稿类失败优先 `business_prose_first`；定稿形态失败优先 `manuscript_form_cleanup`（先合稿去横幅）。同一问题再次失败时更换重构方向；达到上限后保留最佳稿、缺口清单和决策选项。
