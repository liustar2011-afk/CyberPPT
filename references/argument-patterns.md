# PPT Argument Patterns

Use these after analysis has identified a defensible source-supported relationship. `.agents/skills/cyberppt-script-understand/references/analysis-models.md` helps discover latent logic; this file helps turn validated logic into a page argument.

## Selection rule

A pattern is valid when it clarifies how the page establishes its message. Do not force content into causality, chronology, ranking, dependency, symmetry or progression that the source cannot support.

## 1. Definition / positioning

`definition -> components -> boundary -> function / role`

## 2. Situation–tension–response

`situation -> pressure / tension -> implication -> response need`

Use for background pages when the source supports a real tension. The tension may be inferred from source facts if its support is recorded.

## 3. Necessity / diagnosis

`current state -> problem -> cause / constraint -> bounded necessity`

Avoid necessary-condition language unless the source supports it.

## 4. Mechanism

`input / actor -> mechanism -> state change -> output / effect`

## 5. Problem-to-response mapping

`problem dimension -> response capability -> role / effect`

An inferred mapping is allowed when it is analytically clear; label it as inferred rather than presenting it as an explicit source statement.

## 6. Architecture

`objects -> layers / interactions -> services -> outputs`

Architecture can be layered, networked or grouped. Do not imply vertical dependency between peer categories.

## 7. Value

`capability -> application -> deliverable -> beneficiary -> value`

## 8. Classification / taxonomy

`classification dimension -> peer categories -> distinguishing attributes -> coverage / implication`

Use when the source genuinely presents peer service types, actors, resources or modes. Classification is a complete analytical structure and does not require artificial arrows.

## 9. Comparison / selection

`common dimensions -> alternatives -> differences -> implication`

## 10. Decision

`decision question -> criteria -> evidence / trade-offs -> recommendation / boundary`

## 11. Progression / maturity

`starting state -> transition condition -> next state -> scale / outcome`

Use only when transition conditions or maturity progression are source-supported. Preserve any statement that modes may also be adopted independently.

## 12. Policy response

`policy / standard requirement -> organizational task -> project response -> expected result`

## 13. Implementation

`phase / condition -> task -> output -> gate`

## 14. Operating loop

`participant -> service -> delivery / use -> transaction / feedback -> continued operation`

## 15. Governance / responsibility

`actor -> responsibility / authority -> controlled object -> rule / boundary -> accountable outcome`

## 16. Evidence synthesis

`claim -> evidence set -> interpretation -> bounded implication`

This is a high-value pattern for formal Word material because it can surface an insight while keeping the underlying facts unchanged.

## Relation rule

Every material arrow or dependency should be `explicit` or `inferred` with support. `speculative` relations are excluded. Visual relationships handed to Stage 02 follow the same rule.
