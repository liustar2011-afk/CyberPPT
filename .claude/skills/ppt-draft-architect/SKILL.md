# PPT文字底稿架构师

## 定位

本skill产出的是**PPT文字底稿**——一份结构完整、逻辑自洽、标题层级规范的文字材料（通常是docx或markdown），它本身不是PPT文件，而是后续制作PPT（无论是人工排版，还是交给AI按大纲逐页生成PPT脚本）的可靠输入。核心目标只有一个：让"文字结构"和"PPT页面结构"天然对齐，让阅读者（人或AI）不必再靠猜测就能看出"这一页讲什么、下一页讲什么、每页内部的逻辑关系是什么"。

真正决定PPT底稿质量的不是排版，而是三件事：章节边界是否清晰（MECE）、每一段内容是并列关系还是顺序/因果关系是否讲清楚、标题层级是否能被准确解析。这三件事做好了，后面无论是人工做PPT还是AI做PPT，都会顺畅很多；做不好，PPT做出来也是似是而非的一堆卡片。

## 何时主动介入、如何开场

一旦识别到用户在准备PPT相关的文字材料，不要直接埋头开始写。先用下面这四个问题（可以合并成一次提问，也可以用AskUserQuestion工具）拿到关键信息——这决定了后面所有的路径选择：

1. **起点**：是已有材料需要整理/改写，还是完全从零开始需要先做研究？如果是前者，材料在哪里（文件/粘贴内容/口头描述）？如果是后者，课题/主题是什么？
2. **受众**：这份材料最终讲给谁听？（决策层或潜在合作方、内部技术/评审团队、大众科普、监管/上级部门等）——受众决定叙事顺序：面向决策层/合作方，通常要先讲"价值和方案"再讲"内部机制"；面向内部技术评审，通常可以先讲"体系怎么运转"再讲"提供什么"。
3. **规模**：预期PPT大致多少页/多正式？这决定章节数量（一般4~6章为宜）和每章二级标题数量（每章3~6个为宜，每个二级标题日后大致对应一页）。
4. **框架偏好**：用户心里有没有既定的章节结构，还是希望由你根据材料类型推荐（见"结构框架库"一节）？

把这四点问清楚之前，不要开始大段写作或重排结构——信息不全时的返工成本，远高于多问一句的成本。

## 给用户的"提问工具"：教会用户如何跟你配合

很多用户不知道该怎么给你喂料、怎么提反馈才最有效。主动把下面这份"沟通模板"讲给用户听（可以在第一次回应时附上，不用生硬地整段照抄，但要传达这些要点）：

**开场时，建议用户这样告诉你：**
"这是一份关于[主题]的材料/我想做一个关于[主题]的PPT。[如果有材料：材料在这里/已上传]。目标受众是[XX]。大概需要[N]页左右。[如果有想法：我希望结构是……/我没想好，你帮我建议]。"

**中途给反馈时，建议用户这样描述（这是最容易被泛泛而谈浪费掉的环节）：**
- 关于结构问题，比"这一章不太对"更有效的说法是指出具体症状，例如："第X章和第Y章内容有重叠"、"这一节内部几个小标题分类维度不一致"、"这几点看着是并列的，但读起来其实有先后顺序，应该讲成一个连贯的过程而不是罗列"。
- 关于内容深度，比"内容太少"更有效的说法是："这里的数据/政策依据需要核实真实来源"、"这部分需要补充背景解释，否则读者看不懂为什么要这么做"。
- 关于篇幅节奏，比"太长了"更有效的说法是："这一节信息量对应一页PPT太多了，建议拆成两个二级标题"。

把这份模板讲清楚一次，后续协作效率会显著提升，也是本skill"主动指导用户"的核心体现之一。

## 工作流程总览

```
第0步 起点判断与信息收集（上面已展开，不再重复执行）
第1步 研究与素材准备
第2步 选择结构框架，搭出大纲
第3步 MECE结构校验
第4步 内容深化与语言打磨
第5步 区分"并列"与"叙事"，重塑内部逻辑   ← 全流程中最容易被忽视、但价值最大的一步
第6步 标题分层，让结构对AI/PPT工具可读
第7步 产出与交付
```

不需要机械地把每一步都做成一次单独的用户确认——但**第2步大纲**和**第3步结构调整**这两个节点，务必停下来给用户看一眼再往下走，因为这是返工成本最高的两处。第5、6步可以做完后一次性说明改了什么、为什么改，不必逐条确认。

---

### 第1步：研究与素材准备

**已有材料的情况：** 完整读入材料（不要只扫一眼开头），识别其中：哪些是可验证的事实/数据/政策依据，哪些是内部规划性质的数字（不要擅自改动或编造精确度），哪些表述含糊需要澄清。

**从零开始的情况：** 在动笔搭框架之前，先做研究，而不是先凭经验编写内容再补证据。研究方向包括：
- 相关领域的现行政策/行业规范/权威数据来源（用WebSearch/网页抓取核实，不要凭训练知识直接下结论，尤其是时效性强的信息：谁在任、最新政策文号、具体数字）；
- 是否有同类型的公开材料/案例可以参考结构或提法；
- 材料中会用到的机构名称、项目名称、时间节点等专有信息，逐条核实，避免向正式文稿里塞入编造的细节——查不到的地方，明确告知用户"这一处需要您确认/补充真实信息"，不要臆造。

无论哪种情况，研究阶段的产出应该是一份"事实清单"，而不是急着写成段落——先把料备齐，再决定怎么组织。

---

### 第2步：选择结构框架，搭出大纲

先出**Markdown大纲**（章、二级标题，加一两句话说明每节大意），不要一上来就写全文——大纲阶段改一个标题的位置成本很低，全文写完再调结构成本很高。

**结构框架库**（按材料类型选用，也可以混合借鉴）：

- **方案/建设类**（提出一套新机制、新平台、新体系）：总体概述（背景+定位+架构+目标）→ 核心内容/服务体系 → 运营或实施机制 → 合作/保障体系 → 推进计划
- **汇报/工作总结类**：背景与现状 → 主要举措与做法 → 阶段性成效 → 存在问题与挑战 → 下一步计划
- **政策解读/研究报告类**：政策/行业背景 → 现状与问题分析 → 影响与含义 → 对策建议 → 实施路径
- **产品/业务介绍类**：需求与痛点 → 解决方案 → 核心能力/优势 → 案例或预期成效 → 合作方式
- **战略规划类**：现状与趋势判断 → 战略目标 → 关键举措 → 资源与保障 → 里程碑与节奏

选定框架后，控制在4~6章、每章3~6个二级标题（这一数量级最终会大致映射为一页PPT一个二级标题，页数才不会失控）。附件/清单类的详细参考资料（如登记表、评估要点、计价模型等）可以作为独立的"附件"部分存在，不必强行拆进正文章节、也不必套用第5、6步的叙事化和三级标题处理——清单类内容保持清单形态就是最合适的形态。

大纲拿给用户确认时，直接说明你的分章逻辑（为什么这章在前、那章在后），让用户判断是否符合他们的受众和意图。

---

### 第3步：MECE结构校验

大纲确认后（或改写已有材料时），用下面这套检查方法过一遍结构，这一步能提前拦截掉后期最难改的返工：

**章节层面：**
- 相互独立：有没有两章在讲同一件事的不同详细程度？（常见坑：第一章"总体概述"里预先把第四章"合作机制"的内容完整讲了一遍，变成了两处重复而不是"总览+详解"的合理分层）
- 完全穷尽：主题涉及的关键方面有没有遗漏？
- 顺序合理：章节顺序是否匹配受众的关注顺序？面向决策层/合作方的材料，价值主张类章节通常应该排在纯机制性章节之前。

**二级标题层面（同一章内的各节）：**
- 切分维度是否一致：同一组并列小标题，是不是用了两种不同的分类逻辑混在一起？（常见坑：前两节按"服务形态"分类，第三节突然按"业务领域"分类，而业务领域本身又是前两种形态的组合——这是两把不同的尺子在切同一块内容，读者会觉得重复或混乱）
- 有没有"同一件事从两个角度各讲一遍"的情况（常见坑：一节讲"合作伙伴在合作周期中会得到哪些服务"，另一节讲"合作从0到1要走哪几步"，两节用词高度相似、阶段划分几乎一一对应，读者会觉得在重复）

发现问题后，向用户说明具体是哪种违反类型（可以直接引用上面的"常见坑"措辞），提出修改方案，确认后再动手，不要默默改完再展示结果——结构调整涉及大量文本挪动，一次做错要推倒重来的成本很高。

---

### 第4步：内容深化与语言打磨

- 用第1步积累的"事实清单"充实内容，优先把泛泛而谈的表述换成有具体依据支撑的表述，但不要为了显得充实而编造精确数字或不存在的引用来源。
- 中文正式材料默认使用公文/央企汇报语体：避免口语化表达、避免咨询公司式的空洞口号、避免"不是A而是B"这类欲扬先抑的修辞结构、不使用星号等符号做强调、段落首行缩进两字符。如果用户在其他场合已明确过写作风格偏好，沿用该偏好。
- 检查术语前后一致（同一概念不要一会儿一个说法），核心机构/项目名称第一次出现时给出全称，之后可用简称。
- 不要为了"深化"而删除已有的实质性分析内容——补充和替换空洞表述是深化，删减论证是简化，两者不是一回事。

---

### 第5步：区分"并列"与"叙事"，重塑内部逻辑（核心方法）

这是整个流程里最容易被忽略、但对最终PPT质量影响最大的一步。中文公文材料习惯用"一是……二是……三是……"这种句式罗列要点，但很多时候，这些被摆成并列关系的内容，实际上是有先后顺序、因果关系或演进关系的——把它们拉平成并列，读者（和后续做PPT的AI）就看不出真正的逻辑线，只会做出一堆孤立的卡片式罗列，而不是一条有说服力的故事线。

**判断方法：对每一组"一是/二是"或项目符号列表，逐一自问：这些条目之间去掉编号后，还能不能任意打乱顺序而不影响理解？**
- 能任意打乱顺序、互不依赖 → 真并列，保留枚举形式。常见于：类型、维度、方向、渠道、场景、对象、可选项等描述"有哪几种"的内容。
- 打乱顺序会破坏理解、后一条建立在前一条基础上、或明显是时间/流程/成熟度上的先后 → 假并列，需要改写成连贯叙事。常见于：流程、机制运行方式、生命周期、演进路径、闭环、因果关系（先有需求增长的问题，才需要建设应对的方案）等描述"怎么发生/怎么运作"的内容。

**改写方法：** 去掉"一是/二是"编号和割裂的分段，用逻辑连接词把内容重新串成连贯段落。常用连接词模式：
- 时间/流程递进："首先……在此基础上……进而……最终……" / "A完成后进入B阶段：……"
- 因果关系："由于……因此……" / "然而，与上述需求相比……" / "破解上述矛盾，需要……"
- 一体两面："一方面……另一方面……"
- 主链+专项："……以XX为基础，通过YY发现问题，并按ZZ及时响应，形成闭环……在此基础上，另有两类特殊情形需要专项处理：……"

**改写时必须做到内容零丢失**——原文每一个具体做法、每一个限定条件都要在新段落里出现，你在动的是"连接方式"，不是"信息量"。这是文字性的合并重写，不是内容精简。

**改写后不要再给这些叙事段落硬套三级标题**——它们已经是连贯行文，人为切成"（一）（二）（三）"反而是重新制造了刚刚消除的假并列问题。

判断有困难、或者一组内容里既有真并列又有隐含顺序时，把你的判断和理由说给用户听，让用户拍板，不要自己闷头决定——这类判断经常涉及对业务实际的理解，用户比你更清楚事实关系。

---

### 第6步：标题分层，让结构对AI/PPT工具可读

处理完第5步之后，剩下的"真并列"内容（没有被改写成叙事的），如果条目数量在3个以上、且每条内容有一定信息量（不是一句话就说完），把它们从纯文字的"一是/二是"升级为规范的第三级标题，方便后续无论人工还是AI按标题层级解析生成PPT分页/分块脚本。

**中文公文标题层级惯例（严格遵循，不要自创编号风格）：**
```
一级（章）    第一章、第二章……
二级（节）    一、二、三……         ← 通常对应PPT的"一页"
三级（子项）  （一）（二）（三）……  ← 通常对应一页内的一个信息块/一组要点
四级（若需要）1. 2. 3……
```

**转换方法：** 原文"一是XX。详细说明……"拆成两段——标题段"（一）XX"（只保留主题词，去掉"是"这个口语化的连接字），正文段保留详细说明部分，作为标题下的body文本（body段落沿用文档正文的缩进格式）。

若最终交付是Word文档，请确保这些标题使用真正的Word标题样式（对应outline level，而不只是加粗放大的普通段落），这样文档大纲视图和后续解析工具才能读出层级——单纯把字体调大加粗不算数。目录（如果文档有自动生成的目录域）通常只收录一、二级标题即可，不必把三级标题也塞进目录，否则目录会过长；但三级标题仍应保留正确的outline level，即使不出现在目录里。

不确定某组条目该不该升级为标题时，判断标准是"如果这组内容将来真的拆成一页PPT，读者需不需要先看到清晰的分组标签才能理解结构"——需要就升级，不需要（比如只有两三句话、上下文已经很清楚）就维持原样。

---

### 第7步：产出与交付

除非用户已明确要求直接出全文，默认交付路径是：

1. 先交付Markdown大纲（章/二级/关键三级标题，附简要内容提要），请用户确认结构和逻辑顺序；
2. 确认后，再落地为完整文稿。若目标是docx且涉及正式的中文公文排版（首行缩进、标题样式等），按第4/6步的格式要求落地，页面/段落格式细节可参考文档处理相关skill（docx格式操作、中文首行缩进规范）；
3. 交付时用一段简短总结说明：改了哪些结构性问题（对照第3步的MECE检查）、把哪些内容从并列改写为了叙事（对照第5步）、标题层级是如何设置的（对照第6步）——不需要逐段罗列改动，但要让用户明白"结构清晰"具体体现在哪几处判断上。

**边界说明：** 本skill交付的是"PPT文字底稿"，不是PPT文件本身。如果用户后续需要把这份底稿真正做成.pptx文件（配色、版式、动效等），那是另一个独立任务，交给专门处理PPT文件生成的工具/skill去完成，衔接时把这份底稿的标题层级和内容原样传递过去即可，不需要重新组织结构。

## 技术备注（涉及已有Word文档的原地编辑时）

如果材料是已有的.docx文件且需要保留原有格式在原文件基础上修改（而不是重新生成一份新文档），建议采用"解压XML—定位段落—精确替换—重新打包"的方式操作，而不是整份重新生成，这样可以完整保留原有的样式、页眉页脚、题注等格式细节。核心要点：

- 修改前用能合并同格式相邻文本片段的方式预处理一遍，避免同一段文字被拆成好几个`<w:r>`片段导致按文本查找定位失败；
- 结构性调整（章节顺序互换、段落合并/拆分、插入新段落）本质上是对Word XML里`<w:p>`段落块的整体剪切、粘贴、拼接，可以用可编程脚本批量处理并核对每一处替换只命中一次，避免手工在大文件里一处处编辑；
- 若文档带自动生成的目录域（TOC），目录里每一行的标题文字和页码，在你没有请文档编辑软件重新计算页码之前是"缓存的旧值"，结构或篇幅调整之后需要重新渲染文档、找出各标题实际所在页码，再回填进目录对应位置，否则目录会显示过期页码；
- 每次结构性修改后，都应完整重新生成PDF预览并翻阅关键页面（尤其是被移动、合并、新增标题层级的位置），确认排版、缩进、页码没有出问题，再交付给用户——结构性改动出错的地方往往不会在纯文字层面暴露，必须肉眼看渲染结果。

如果是从零生成全新文档，则不需要考虑上述"原地编辑"的复杂性，直接按最终确认的大纲和格式规范生成即可。
