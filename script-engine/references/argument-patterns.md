# PPT Argument Patterns

Use these as reasoning grammars, not rigid page templates. Select the pattern that best answers the audience question and preserve source-supported relationships.

## Definition

`definition → components → boundary → function`

Use when the page must explain what something is and where its scope ends.

## Necessity

`current state → problem → cause → necessity`

Use when the page must establish why an action, project, or capability is required.

## Mechanism

`input → mechanism → state change → output`

Use when explaining how a system, policy, process, or capability works.

## Solution

`problem → response mechanism → capability → result`

Use when the page must connect a problem to a concrete solution.

## Architecture

`objects → inputs → processing / interaction → services → outputs`

Use for systems, platforms, data infrastructure, operating mechanisms, and service architectures.

## Value

`capability → application → deliverable → beneficiary / decision value`

Use when explaining business or institutional value.

## Comparison

`evaluation dimensions → alternatives → material differences → conclusion`

Use only when the source supports a genuine comparison.

## Progression

`foundation → enabling mechanism → application → outcome`

Use for maturity, transformation, or capability build-up.

## Policy response

`policy requirement → industry task → project response → expected result`

Use when mapping policy requirements to concrete program actions.

## Implementation

`phase → task → output → dependency / gate`

Use for delivery and implementation plans where sequence is source-supported.

## Operating loop

`customer / participant → service → delivery → usage / transaction → feedback / revenue → continued operation`

Use for service operations and sustainable operating models.

## Evidence rule

The selected pattern is valid only when its links are supported by the source foundation. Do not invent causality, chronology, priority, or dependency merely to fit a pattern.
